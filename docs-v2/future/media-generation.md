# Future — Media Generation (Image and Audio)

> **Status:** Design captured for v2.1 — **not implemented in v2.0**
> **Captured:** 2026-04-29 from a Doc 19 design session
> **Replaces in v2.0:** Nothing. The schema enum value `messages.content_type = 'blocks'` exists for forward compatibility; the `telemetry` rows for `image_gen` and `tts` exist and stay at zero.

This document captures the v1.0 image-generation and TTS design (`PRDs/20-Media-System-Image-Generation.md` and the inline-image-in-message-bubble portions of `PRDs/19-Media-System-Image-Uploads.md` + PATCH-19) and outlines the redesign required to fold them into the v2.0 modes / cache / `isGenerating` architecture.

When v2.1 work begins, start here. Provider decisions (Q1 / Q2 in `docs-v2/TODO.md`) must land first; everything else is design-complete and waiting on them.

## v1.0 Spec (verbatim summary)

The full PRD is `PRDs/20-Media-System-Image-Generation.md`. Carry-forward summary:

### Per-send toggle

A toggle button in the Theater input area, left of Send. When on:
1. Text generation proceeds as normal.
2. A second Gemini call extracts a structured scene description from the produced text.
3. The scene description is sent to the configured `ImageGenerationProvider`.
4. The returned image is saved to `assets/` and appended as an `image` block at the end of the AI message content.

State: per-story, `story_settings.img_gen_enabled`. (In v2.0, `story_settings` was renamed `story_state`; the equivalent v2.1 placement is TBD — likely a boolean field on `story_state` or on a per-mode settings cascade.)

### Selected-text → image

When the writer has a text selection in any AI bubble, an action-row "Generate Image from Selection" button (`lucide-react Sparkles`) becomes available. The selected text + full message content is fed to Gemini for scene description, then to the image provider; the returned image is inserted as an `image` block immediately after the selected passage.

### Scene description extraction (Gemini)

Before any image provider call, Gemini extracts a structured scene description:

```
System: You are a visual director. Given a passage of prose, extract the single
most visually compelling scene or moment. Output only JSON, no preamble.

User: <passage>{text}</passage>

JSON schema:
{
  "subject": string,
  "setting": string,
  "mood": string,
  "lighting": string,
  "style_notes": string
}
```

The structured output is then formatted into the provider's expected prompt shape.

### `ImageGenerationProvider` Rust trait

```rust
#[async_trait]
pub trait ImageGenerationProvider: Send + Sync {
    fn name(&self) -> &str;
    fn requires_api_key(&self) -> bool;
    async fn generate(&self, scene: &SceneDescription) -> Result<GeneratedImage, LoomError>;
}

pub struct GeneratedImage {
    pub bytes: Vec<u8>,
    pub mime_type: String,    // "image/png" | "image/jpeg" | "image/webp"
    pub width: u32,
    pub height: u32,
}
```

Provider registry in `services/image_gen.rs`. A switch on `app_settings.image_gen_provider` (a string slug like `"gemini-2-flash"` / `"imagen-3"` / `"stability-sdxl"`) returns the boxed provider.

### `MessageBlock[]` and `content_type = 'blocks'`

When AI image generation appends an image to a model message, the message's `content` becomes a JSON-serialised `MessageBlock[]`:

```ts
type MessageBlock =
  | { type: 'text'; text: string }
  | { type: 'image'; item_id: string; asset_path: string };
```

`content_type` flips from `'text'` to `'blocks'`. The image block references an `Image` vault item that was created during the generation flow (the generated bytes are saved into `assets/` exactly like an uploaded image).

### Tauri commands

| Command | Purpose |
|---|---|
| `generate_image_for_message(message_id)` | Triggered by the per-send toggle after the text generation completes |
| `generate_image_from_selection(message_id, start, end)` | Triggered by the action-row button on text selection |
| `cancel_image_generation()` | Aborts the in-flight image generation |
| `set_image_gen_provider(slug)` | Switches the active provider |
| `set_image_gen_enabled(story_id, enabled)` | Per-story toggle persistence |

Events: `image_generation_started`, `image_generation_complete { message_id, item_id }`, `image_generation_failed { message_id, error_kind }`.

### TTS / audio

`PRDs` has no full TTS spec — only the `telemetry.tts` row exists in v1. The v2.1 design pass will treat TTS analogously to image gen:
- `AudioGenerationProvider` trait.
- Provider slug in `app_settings.tts_provider`.
- TTS produces `audio/*` files into `worlds/<world_id>/assets/` (same convention as images).
- A new `MessageBlock` variant `{ type: 'audio'; item_id: string; asset_path: string }` extends the union.
- Per-message TTS button or per-bubble play affordance — UI TBD.

### Settings UI

Settings → Connections (a new section in Doc 20):
- Provider dropdowns for image and TTS.
- Per-provider API key fields (encrypted in `settings` table like the Gemini API key).
- Per-provider quality / model variant selection.

## What v2.0 changes

The v1.0 design predates several v2.0 architectural decisions. v2.1 needs to fold these in:

1. **Modes (Doc 23, D-10).** Image generation per-send toggle: does it apply only in story mode? Story + handover? Story + handover + consulting? Probably story-only — handover output is structured prose, not narrative; consulting is meta. But user choice should be honoured per-mode.
2. **Caching (Doc 22, D-11).** A model message that ends up as `'blocks'` (text + image) participates in the cache like any other model message. Cache stale rules apply when blocks messages are edited / regenerated. The image bytes themselves don't go into the cached prefix — only the file URI of the saved Image item, same as any source-doc image.
3. **`isGenerating` global lock (D-12).** Image generation calls participate in the single global lock — one model call at a time, including image-gen calls. The send → text → scene-extraction → image-gen sequence is *one* logical operation; cancellation aborts wherever it is.
4. **Ghostwriter on blocks (Doc 17).** PATCH-16 captured the design (text-only concatenation for selection, image blocks preserved by index, `previous_text_blocks` in history). v2.1 implements it alongside image gen.
5. **Doc 18 source-doc inclusion.** AI-generated images become `Image` vault items; they can be attached as Context Documents like any uploaded image. The flow that creates them must call into the standard upload-and-cache path (same `assets/` layout, same `get_or_upload_file_api_uri` cache).
6. **Settings cascade (Doc 03).** Provider slugs and API keys live in `app_settings`. Per-world overrides via `settings` table where appropriate (e.g. a world-specific style preset).

## Open Questions for v2.1

1. **Provider for image gen.** Q1 in `docs-v2/TODO.md`. Gemini 2.0 Flash multimodal is the simplest (no extra API key); Imagen 3 / Stability / fal.ai are paid alternatives.
2. **Provider for TTS.** Q2 in `docs-v2/TODO.md`. ElevenLabs / Google TTS / OpenAI TTS / Kokoro / Piper.
3. **Hardcoded vs user-selectable per media type.** Q3 in `docs-v2/TODO.md`.
4. **Per-mode availability.** Image gen on story only, or also handover / consulting? TTS on any mode's AI output?
5. **Streaming image partial frames.** Some providers stream low-res progressive renders. Worth implementing in v2.1, or non-streaming only?
6. **Cancellation semantics.** Cancel during text-gen-then-image-gen — do we keep the text and discard the planned image? Or cancel both? Lean: keep the text, drop the image (toast: "Image generation cancelled; text saved").
7. **Re-generation of just the image.** A `Regenerate image` action on a `'blocks'` message that re-runs only the image step (preserving text + scene extraction)?
8. **Multiple images per message.** v1 inserted at most one image at message end (per-send toggle) or one image after a selection (selected-text flow). v2.1 may want multiple — at every scene break, every chapter end, etc.
9. **Image-gen cost surfacing.** For paid providers, surface estimated cost per generation in the toggle tooltip?
10. **Per-story provider override.** A world might have a specific aesthetic; per-world `image_gen_provider` override on top of the app default?

## Migration story from v2.0

There is no migration. v2.0 ships without image-gen / TTS code; v2.1 adds the new commands, the provider trait, the Settings UI section, and the per-send toggle. Existing `'text'` content_type messages are unaffected. Existing Image vault items continue to work exactly as before — they just get joined by AI-generated siblings.

`messages.ghostwriter_history` schema is unchanged; v2.1 implements PATCH-16's blocks-aware ghostwriter logic on top of it.
