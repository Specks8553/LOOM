#### CD-01 — Atomic temp-file extension drifts from spec (`.tmp` replaces `.json`)

- **Severity:** CD — Cross-Doc inconsistency
- **Phase:** A1
- **Surface:** `src-tauri/src/services/config.rs:88`, `src-tauri/src/services/world.rs:118`
- **Evidence:**
  - Doc 02 §File System Security: "Atomic write: always write to `app_config.json.tmp`, then `fs::rename` to `app_config.json`."
  - `services/config.rs:88` — `let tmp_path = path.with_extension("tmp");` — produces `app_config.tmp` (extension replaced, not appended).
  - `services/world.rs:118` — `let tmp = path.with_extension("tmp");` — produces `world_meta.tmp` instead of `world_meta.json.tmp`.
- **Observation:** Both atomic-write sites use `Path::with_extension("tmp")`, which strips the `.json` and yields `app_config.tmp` / `world_meta.tmp`. Functionally correct (`rename` is still atomic on the same filesystem), but the file the spec names (`app_config.json.tmp`) never exists on disk. A future operator following Doc 02 to debug a half-written state would look for the wrong file.
- **Proposed lean:** Change to a string concat (`format!("{}.tmp", path.display())`) or use `Path::with_added_extension` (nightly) so the on-disk temp file is `<filename>.tmp`. Trivial; same site already does atomic rename.
- **Cross-refs:** none

#### SD-01 — `conversation_sessions.entry_message_id` missing FK clause in migration

- **Severity:** SD — Schema drift
- **Phase:** A1
- **Surface:** `src-tauri/src/db/migrations/world/001_initial.sql:33`

- **Evidence:**

#### HB-01 — Ten of eleven `LoomError` variants cannot be serialized across IPC (serde internally-tagged newtype-of-`String` limitation)

- **Severity:** HB — Hard Blocker (first HB of this audit; runtime correctness defect in the foundational IPC error contract)
- **Phase:** B5
- **Surface:** `src-tauri/src/error.rs:6-46`; `src-tauri/src/lib/types.ts:106` (ts-rs reference output); 112 command sites returning `Result<T, LoomError>` (commands/{vault,conversation,modes,settings,accordion,cache,ghostwriter,auth,app_phase}.rs)
- **Evidence:**
  - `error.rs:6-9` — `#[derive(… Serialize …)] #[serde(tag = "kind", rename_all = "snake_case")] pub enum LoomError {`
  - `error.rs:10-45` — ten of the eleven variants are newtype variants wrapping a bare `String`: `Crypto(String)`, `Database(String)`, `NotFound(String)`, `Forbidden(String)`, `ApiError(String)`, `CacheCreate(String)`, `RateLimited(String)`, `Io(String)`, `Serialization(String)`, `Internal(String)`. Only `Validation { … }` is a struct variant.
  - serde's internally-tagged representation (`#[serde(tag = "…")]`) **cannot serialize a newtype variant whose inner value is a string/primitive** — at runtime `serialize_tagged_newtype` returns `Err("cannot serialize tagged newtype variant LoomError::<V> containing a string")`. Only unit, struct, and newtype-of-map/struct variants are supported.
  - Independent corroboration from the same toolchain: `src-tauri/src/lib/types.ts:106` (ts-rs `#[ts(export)]` output) renders each String variant as the nonsensical intersection `{ "kind": "crypto" } & string | { "kind": "database" } & string | …`, while the one struct variant renders correctly as `{ "kind": "validation", validation_kind: ValidationKind, key: string | null, reason: string, }`. ts-rs emits `& string` precisely for the serde pattern it cannot represent — the asymmetry mirrors the runtime serialization asymmetry exactly.
  - No custom `impl Serialize for LoomError` exists (grep clean) — the derived impl is authoritative.
- **Observation:** Every Tauri command in the app returns `Result<T, LoomError>`. When a command fails with any of the ten String variants (i.e. all of them except `Validation`), Tauri serializes the error via `serde_json` to send it to JS — and that serialization fails at runtime because serde cannot represent an internally-tagged newtype-of-`String`. The structured `{ kind, message }` object the frontend's `types.ts` and Doc 12 both assume **never crosses the boundary**; the JS `invoke()` rejection receives the serde meta-error string instead (or whatever Tauri substitutes when error serialization fails), not the intended error. The app degrades rather than crashes (a generic fallback toast still fires — see CD-33), but all real error detail and the `kind` discriminator are lost for 10/11 variants. This makes Doc 12 §Error Display Hierarchy (kind-keyed surface/copy routing) unbuildable as designed and silently defeats any future error-kind-dependent feature (rate-limit handling per CQ-05, cache-create failures, API-key validation). The struct-variant `Validation` is the only one that would serialize cleanly.
- **Proposed lean:** Switch the enum to an **adjacently-tagged** representation — `#[serde(tag = "kind", content = "message")]` — which serde *can* serialize for newtype-String variants (produces `{ "kind": "crypto", "message": "…" }`), then regenerate ts-rs and reconcile the hand-maintained `src/lib/types.ts` (the latter is already drifted — see SB-01/SB-02). Add a unit test serializing each variant with `serde_json::to_string` to lock the contract (Doc 25 expects error-path coverage). **Verify empirically in remediation** — write the serialization test first to confirm the runtime failure before changing the representation. Whichever representation is chosen, Doc 03/05/07 IPC-contract docs must record it.
- **Cross-refs:** SB-01, SB-02 (hand-maintained `types.ts` drift — its `LoomError` is also missing four variants and has wrong `Validation`/`ValidationKind` shapes), CD-33 (frontend never reads the structured error regardless), DG-06 (Doc 12 has no variant↔rule matrix)
